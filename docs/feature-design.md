# 여백 미장원 추가 기능 설계안

현재 앱의 한계(브라우저 저장, 관리자 로그인 없음, 예약 상태 변경 불가 등)를 기준으로, 우선순위별 추가 기능과 구현 설계를 정리했습니다.

## 1. 현재 한계와 해결 방향

| 현재 한계 | 영향 | 해결 기능 |
| --- | --- | --- |
| 데이터가 브라우저 LocalStorage에 저장 | 고객이 접수한 예약이 매장 PC에 보이지 않음, 브라우저 삭제 시 유실 | 서버 DB 저장 (A-1) |
| 관리자 화면에 로그인 없음 | 누구나 관리자 화면 접근 가능 | 관리자 로그인 (A-2) |
| 예약 상태가 항상 대기 | 확정·취소·완료를 구분할 수 없음 | 예약 상태 관리 (B-1) |
| 예약 삭제 시 코인 미환불 | 수동 정정 필요 | 취소 시 코인 자동 환불 (B-2) |
| 고객 예약 변경·취소 수단 없음 | 전화로만 처리 | 고객 예약 조회·취소 (B-3) |
| 방문 횟수·최근 방문 수동 | 고객 이력 부정확 | 시술 완료 처리 (B-1) |
| 네이버 캘린더는 일정 추가만 가능 | 변경·삭제가 반영 안 됨 | 캘린더 피드 (C-5) |

## 2. 기능 목록과 우선순위

| 단계 | 기능 | 핵심 효과 |
| --- | --- | --- |
| A. 기반 | A-1 서버 DB 저장, A-2 관리자 로그인 | 실제 운영 가능한 상태 |
| B. 운영 | B-1 예약 상태 관리, B-2 코인 자동 처리, B-3 고객 예약 조회·취소, B-4 문자 알림 | 원장님 수작업 감소 |
| C. 확장 | C-1 메뉴·가격 관리, C-2 영업시간·휴무일, C-3 디자이너별 시간표, C-4 매출 통계, C-5 캘린더 피드, C-6 고객 메모·시술 이력, C-7 후기 개선 | 매장 운영 고도화 |

## 3. 기능별 설계

### A-1. 서버 DB 저장

- **방식:** Node 내장 SQLite(`node:sqlite`, Node 22.5 이상)로 단일 파일 DB를 사용합니다. 포레스트클럽도 SQLite를 쓰고 있어 운영 방식이 같습니다. 의존성 추가가 없습니다.
- **API:** 프런트는 LocalStorage 대신 서버 API를 호출합니다.

| 메서드 | 경로 | 용도 |
| --- | --- | --- |
| GET | `/api/slots?date=` | 날짜별 예약 가능 시간 |
| POST | `/api/reservations` | 예약 접수 (서버에서 중복·코인 검증) |
| GET | `/api/admin/reservations?month=` | 관리자 캘린더 |
| PATCH | `/api/admin/reservations/:id` | 상태 변경 |
| GET/POST | `/api/admin/customers`, `/coins` | 고객·코인 |
| GET/POST | `/api/reviews` | 후기 |

- **핵심 규칙:** 시간 중복 검사와 코인 차감을 **서버 트랜잭션**으로 처리해 두 사람이 같은 시간에 예약하는 문제를 막습니다.
- **이전:** 기존 LocalStorage 데이터는 관리자 화면의 "가져오기" 버튼으로 JSON을 한 번 올려 이전합니다.
- **백업:** DB 파일을 하루 1회 날짜별 복사(7일 보관)합니다.

**테이블**

| 테이블 | 주요 컬럼 |
| --- | --- |
| customers | id, name, phone(고유), coins, visits, last_visit, memo |
| reservations | id, customer_id, date, time, service_id, designer_id, status, price, coin_used, memo, created_at |
| coin_history | id, customer_id, type(add/use/set/refund), amount, balance, reason, reservation_id, created_at |
| reviews | id, name, rating, service, text, status(게시/숨김), created_at |
| services | id, name, price, minutes, active |
| designers | id, name, active |

### A-2. 관리자 로그인

- 관리자 화면 진입 시 비밀번호(또는 기존 `ADMIN_KEY`)를 입력받아 서버가 **HttpOnly 세션 쿠키**를 발급합니다.
- `/api/admin/*` 는 세션이 없으면 401을 반환합니다. 화면 숨김만으로는 보호되지 않으므로 서버에서 반드시 검사합니다.
- 로그인 실패 5회 시 10분 잠금, 세션 유효 8시간.
- 직원 계정 구분(원장/디자이너)은 이후 확장 항목으로 둡니다.

### B-1. 예약 상태 관리

- **상태:** 대기 → 확정 → 완료, 또는 취소 / 노쇼.
- 관리자 캘린더의 상세 목록과 전체 예약 표에서 버튼으로 변경합니다.
- 캘린더 미리보기 색: 대기(노랑), 확정(초록), 완료(회색), 취소·노쇼(빨강, 시간표에서는 다시 예약 가능).
- **완료 처리 시 자동 반영:** 방문 횟수 +1, 최근 방문일 갱신, 적립 코인 지급(B-2).

### B-2. 코인 자동 처리

- **취소·노쇼 시 환불:** 예약에서 사용한 코인을 자동 환불하고 내역에 "예약 취소 환불"로 기록합니다.
- **적립:** 완료 처리 시 실결제 금액의 N%를 적립합니다. 적립률은 관리자 설정 값입니다. (예: 5%)
- **코인 유효기간(선택):** 적립일로부터 12개월. 만료 예정 코인은 문자로 안내합니다.

### B-3. 고객 예약 조회·취소

- 로그인 없이 **연락처 + 문자 인증번호**로 본인 확인 후 자기 예약을 조회합니다.
- 방문 24시간 전까지는 고객이 직접 취소·시간 변경을 할 수 있고, 이후에는 전화 안내 문구를 보여 줍니다. (현재 안내 문구 "하루 전까지"와 동일 규칙)
- 취소 시 B-2의 코인 환불이 자동으로 실행됩니다.

### B-4. 카카오톡·문자 알림

- **구현 상태:** 카카오 알림톡 발송(접수 자동, 확정·취소·방문 안내 관리자 버튼, 방문 전날 자동 안내)은 구현되어 있습니다. 포레스트클럽과 같은 Solapi 방식이며, 설정이 없으면 로그만 남기는 테스트 모드입니다. 사용법은 관리자 매뉴얼 5-2장에 있습니다.
- **남은 범위:** 발송 이력 화면과 재발송, 원장님께 보내는 신규 예약 알림. 현재 자동 방문 안내는 서버가 받은 예약 사본을 기준으로 하므로, 예약 상태를 서버 DB로 일원화(A-1)하면 확정·취소·삭제가 자동으로 정확히 반영됩니다.
- **발송 시점:** 예약 접수 확인, 예약 확정, 방문 전날 리마인드, 취소 안내. 원장님께는 신규 예약 알림을 보냅니다.
- 발송 실패는 관리자 화면에 표시하고, 관리자 화면에서 "재발송"을 제공합니다.
- 발송 비용이 발생하므로 종류별 켜기/끄기 설정을 둡니다.

### C-1. 메뉴·가격 관리
시술 메뉴, 가격, 소요 시간을 관리자가 화면에서 추가·수정·비활성화합니다. 현재는 `index.html`에 고정되어 있습니다.

### C-2. 영업시간·휴무일
정기 휴무 요일, 임시 휴무일, 요일별 영업시간을 설정합니다. 예약 화면의 시간표는 이 설정으로 자동 생성되며, 휴무일은 달력에서 선택할 수 없게 합니다.

### C-3. 디자이너별 시간표와 소요 시간

- 현재는 디자이너와 관계없이 같은 시간에 예약 한 건만 받습니다. 디자이너별로 시간표를 분리하면 같은 시간에 서로 다른 디자이너의 예약을 받을 수 있습니다.
- 시술 소요 시간(예: 커트 60분, 염색 150분)만큼 연속된 슬롯을 점유하도록 바꿉니다.
- "지정 없음"은 그 시간에 가능한 디자이너를 자동 배정합니다.
- 네이버 캘린더 일정 길이도 소요 시간에 맞춥니다. (현재는 1시간 고정)

### C-4. 매출 통계
대시보드에 일·주·월 매출, 시술별 건수, 디자이너별 실적, 신규/재방문 비율, 노쇼율, 코인 발행·사용 합계를 표시합니다. 기준은 **완료** 상태의 예약입니다.

### C-5. 캘린더 피드 (네이버 캘린더 한계 보완)
네이버 캘린더 API는 일정 추가만 가능해서, 서버가 예약 목록을 **iCal 구독 주소(.ics)** 로 제공합니다. 휴대폰 캘린더 앱에 구독하면 취소·변경이 자동 반영됩니다. 구독 주소에는 추측할 수 없는 토큰을 포함합니다. 네이버 연동은 선택 사항으로 유지합니다.

### C-6. 고객 메모·시술 이력
고객 상세 화면에서 방문 이력(날짜·시술·금액·담당), 모발 상태, 알레르기 등 메모를 관리합니다. 개인정보이므로 관리자 로그인 뒤에서만 볼 수 있습니다.

### C-7. 후기 개선

- 관리자 승인 후 게시(선택 설정)
- 완료된 예약이 있는 연락처만 작성 가능 (허위·중복 후기 방지)
- 원장 답글, 사진 첨부(용량 제한)

## 4. 구현 순서 제안

| 순서 | 내용 | 산출물 |
| --- | --- | --- |
| 1 | A-1 + A-2 | 서버 DB, API, 관리자 로그인, 데이터 이전 도구 |
| 2 | B-1 + B-2 | 예약 상태 버튼, 코인 환불·적립 |
| 3 | B-3 + B-4 | 고객 조회·취소, 문자 알림 |
| 4 | C-1 ~ C-3 | 메뉴·휴무·디자이너 관리 |
| 5 | C-4 ~ C-7 | 통계, 캘린더 피드, 고객 이력, 후기 개선 |

1단계가 끝나야 나머지 기능이 의미가 있습니다. 1단계는 앱의 저장 방식이 바뀌므로 가장 큰 작업이고, 이후 단계는 독립적으로 나눠 진행할 수 있습니다.

## 5. 결정이 필요한 사항

1. **적립 정책:** 적립률(예: 5%), 유효기간 적용 여부, 코인 1개 = 1원 유지 여부
2. **문자 알림:** 사용 여부와 발송 종류, 발송 비용 부담
3. **고객 본인 확인:** 문자 인증 사용 여부 (문자 비용 발생) 또는 연락처 뒷자리 확인 방식
4. **디자이너 계정:** 원장 외 디자이너가 각자 로그인해 본인 예약만 볼지 여부
5. **취소 규정:** 노쇼·당일 취소 시 코인 환불 여부
6. **개인정보:** 고객 연락처·메모 보관 기간과 파기 기준, 개인정보 처리 동의 문구
